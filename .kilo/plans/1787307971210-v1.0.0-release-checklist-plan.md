## 2. FIX FRONTEND 404 ROUTES

### Issue 2A: `/portal` route 404

**Problem**: `app/page.tsx:13` and `components/PricingCard.tsx:147,167` link to `/portal`,
but no `app/portal/page.tsx` file exists. Clicking "Download App" produces a Next.js 404.

**Path clarification**: The checklist references `src/app/portal/page.tsx`, but this project
uses `app/` (NOT `src/app/`). The `@/*` tsconfig path maps to `./*` (project root). The
correct path to create is `app/portal/page.tsx`.

**Fix**: Create `app/portal/page.tsx` — a simple landing page with download instructions
or a link to the GitHub releases / install script. Since the `PricingCard` shows a "Download App"
button, this should be a marketing-style page that links to the Tauri desktop installer.

**Verifiable goal**: Visit `http://localhost:3000/portal` → page renders without 404.
The link from `app/page.tsx` ("Download App" button) and `PricingCard.tsx` (two links)
navigates successfully.

### Issue 2B: `src/app/stores/pos/page.tsx`

**Problem**: The checklist asks to ensure `src/app/stores/pos/page.tsx` exists. This appears
to be based on a misunderstanding of the project structure.

**Findings**:
1. The project uses `app/` directory (NOT `src/app/`). The `src/` directory does not exist.
2. The POS page already exists at `app/pos/page.tsx` and exports a valid React component.
3. There is NO navigation link to `/stores/pos` anywhere in the codebase.
4. `stores/posStore.ts` is a Zustand state management store (imported as `@/stores/posStore`),
   NOT a Next.js route page.

**Decision**: No file needs to be created for `src/app/stores/pos/page.tsx`. The equivalent
POS route (`app/pos/page.tsx`) already exists and is valid. The `/stores/pos` path is not
referenced by any navigation link, so no 404 can occur from it.

**Action**: Document this in the plan. If the user specifically wants a `/stores/pos` route,
they should clarify what content it should contain (the POS checkout page already exists at `/pos`).

## 4. FINAL BUILD VERIFICATION

### 4A. Prerequisites

1. **Install Tauri CLI**:
   ```bash
   npm install -D @tauri-apps/cli
   ```
   - **Blocker**: `@tauri-apps/cli` is not in `package.json` and not installed. `npx @tauri-apps/cli build`
     will fail without this.
   - This also requires `@tauri-apps/api` as a runtime dependency if any Tauri APIs are used
     in the frontend (currently `lib.rs` doesn't import any API plugins beyond logging,
     so this may be optional).

2. **Add Tauri scripts to `package.json`**:
   ```json
   "scripts": {
     "tauri": "tauri",
     "tauri:dev": "tauri dev",
     "tauri:build": "tauri build"
   }
   ```

### 4B. Build Sequence

| Step | Command | Expected Output |
|---|---|---|
| 1 | `npm install` | Installs all deps including new `@tauri-apps/cli` |
| 2 | `npm run build` | `next build` → `.next/` directory with production build |
| 3 | `npx @tauri-apps/cli build` | Tauri production build |
| 4 | Verify installer | `.exe` / `.msi` / `.nsis` in `src-tauri/target/release/bundle/` |

### 4C. Expected Installer Output Path

On Windows, Tauri v2 generates installers in:
```
src-tauri/target/release/bundle/msi/PharmacySuite_1.0.0_x64_en-US.msi
# and/or
src-tauri/target/release/bundle/nsis/PharmacySuite_1.0.0_x64_en-US.exe
```

The exact file name depends on `tauri.conf.json` bundle configuration. With
`bundle.targets: "all"` and `bundle.icon` configured, Tauri will produce at minimum
a `.msi` and `.exe` installer.

### 4D. Post-Build Verification

1. Verify installer exists at the output path
2. Verify installer version metadata shows `1.0.0`
3. Verify bundle identifier is `com.pharmacy.suite` (visible in Windows Add/Remove Programs
   or via `wmic` / PowerShell `Get-Package` after install — optional, depends on MSI metadata)
