## 2. PROJECT SCOPE & ARCHITECTURE BLUEPRINT

### 2.1 System Overview

The **Enterprise Pharmacy Management System (EPMS)** is a modern, full-stack enterprise application designed for pharmacy operations. It follows a **decoupled architecture** with a backend REST API and a frontend single-page application.

**Core Value Proposition:** Digitally manage a pharmacy's entire operation — from receiving inventory with batch/expiry tracking, through point-of-sale transactions with FIFO deduction, to role-based access control and remote license management.

### 2.3 Design Patterns

The backend will follow a **Layered/Clean Architecture** with clear separation:

| Layer | Responsibility | Files |
|-------|---------------|-------|
| **API Layer** (`app.api.routers`) | HTTP request routing, validation, response formatting | `*_route.py` |
| **Service Layer** (`app.services`) | Business logic, orchestration, workflow coordination | `*_service.py` |
| **Data Access Layer** (`app.core`) | ORM models, repository patterns, database sessions | `models.py`, `database.py`, `repositories.py` |
| **Shared Utilities** (`app.shared`) | Authentication, logging, config, i18n, error handling | `auth.py`, `config.py`, `logging.py`, `exceptions.py` |

**Patterns Used:**
- **Repository Pattern**: All database queries go through repository classes, not directly through ORM in service layer.
- **Dependency Injection**: FastAPI's `Depends()` system for injecting services, database sessions, and auth context.
- **Observer/Callback Pattern**: For inventory reorder triggers and license webhook events.
- **Template Method Pattern**: For receipt generation (different formats: thermal, PDF, email).

### 2.4 Verifiable Goals (User Journeys)

These are the **only** user journeys the application must support. Every feature must map to one of these goals:

| ID | Goal | Description |
|----|------|-------------|
| **G1** | **POS Checkout** | A cashier scans or searches for a medication, adds it to the cart, applies insurance or payment, and prints/emails a receipt. Inventory is deducted using FIFO (oldest batch first, respecting expiry). |
| **G2** | **Inventory Receiving** | A pharmacist receives a shipment from a supplier. They scan/enter product details, batch/LOT number, expiry date, quantity, unit cost, and supplier. The system creates new batch records and logs the transaction. |
| **G3** | **Inventory Management** | A pharmacist views current stock levels, filters by drug name, batch, supplier, or expiry status. The system displays low-stock alerts and expiring-soon warnings. |
| **G4** | **Role-Based Access** | An admin user manages the system. They create/edit/delete users, assign roles (Admin, Pharmacist, Cashier), and view audit logs. The system enforces permissions on every action. |
| **G5** | **License Activation** | A new customer installs the software, purchases a subscription online, and activates it by entering a license key. The system validates the key against a remote license server and binds it to the local hardware. |

## 4. DATA MODELS, SCHEMAS & STATE MANAGEMENT

### 4.1 Database Schema

The database uses **relational tables** with proper foreign key relationships. Below is the complete schema definition. Implement this via SQLAlchemy ORM models (Section 4.2) and Alembic migrations.

#### Table: `users`
Stores user accounts with role-based permissions.

```sql
CREATE TABLE users (
    id              INTEGER PRIMARY KEY AUTOINCREMENT,
    email           TEXT    NOT NULL UNIQUE,
    full_name       TEXT    NOT NULL,
    hashed_password TEXT    NOT NULL,
    role            TEXT    NOT NULL DEFAULT 'cashier',  -- 'admin' | 'pharmacist' | 'cashier'
    is_active       BOOLEAN NOT NULL DEFAULT TRUE,
    is_licensed     BOOLEAN NOT NULL DEFAULT FALSE,
    created_at      TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at      TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

#### Table: `medicines`
Master catalog of medications.

```sql
CREATE TABLE medicines (
    id              INTEGER PRIMARY KEY AUTOINCREMENT,
    name            TEXT    NOT NULL,           -- "Amoxicillin 500mg Capsules"
    description     TEXT,
    manufacturer    TEXT,                       -- "PharmaCorp"
    unit_of_measure TEXT    NOT NULL DEFAULT 'each',  -- 'each' | 'bottle' | 'box'
    is_controlled   BOOLEAN NOT NULL DEFAULT FALSE,   -- DEA Schedule II-V
    created_at      TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at      TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

#### Table: `batches`
Individual stock batches with lot/expiry tracking (FIFO model).

```sql
CREATE TABLE batches (
    id              INTEGER PRIMARY KEY AUTOINCREMENT,
    medicine_id     INTEGER NOT NULL REFERENCES medicines(id),
    batch_number    TEXT    NOT NULL,           -- Supplier LOT number
    expiry_date     DATE    NOT NULL,            -- YYYY-MM-DD
    purchase_price  REAL    NOT NULL,            -- Cost per unit
    selling_price   REAL    NOT NULL,            -- Retail per unit
    quantity        INTEGER NOT NULL DEFAULT 0,  -- Units in stock (always > 0)
    supplier_id     INTEGER REFERENCES suppliers(id),
    received_at     TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    created_at      TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at      TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);

-- Index for FIFO queries (oldest non-expired batch first)
CREATE INDEX idx_batches_medicine_expiry ON batches(medicine_id, expiry_date, received_at);
```

#### Table: `suppliers`
Supplier/vendor information.

```sql
CREATE TABLE suppliers (
    id              INTEGER PRIMARY KEY AUTOINCREMENT,
    name            TEXT    NOT NULL,
    contact_person  TEXT,
    phone           TEXT,
    email           TEXT,
    address         TEXT,
    created_at      TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

#### Table: `receipts`
Sales transaction headers.

```sql
CREATE TABLE receipts (
    id              INTEGER PRIMARY KEY AUTOINCREMENT,
    receipt_number  TEXT    NOT NULL UNIQUE,    -- "RCP-2026-000001"
    cashier_id      INTEGER NOT NULL REFERENCES users(id),
    patient_name    TEXT,                       -- Optional for OTC
    subtotal        REAL    NOT NULL,
    tax_amount      REAL    NOT NULL DEFAULT 0.0,
    discount_amount REAL    NOT NULL DEFAULT 0.0,
    total_amount    REAL    NOT NULL,
    payment_method  TEXT    NOT NULL,           -- 'cash' | 'card' | 'transfer' | 'insurance'
    payment_status  TEXT    NOT NULL DEFAULT 'completed',  -- 'completed' | 'pending' | 'refunded'
    copay_paid      REAL    DEFAULT 0.0,        -- Patient insurance copay
    insurance_paid  REAL    DEFAULT 0.0,        -- Amount covered by insurance
    sale_type       TEXT    NOT NULL DEFAULT 'OTC',  -- 'OTC' | 'Rx OTC' | 'Delivery'
    created_at      TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

#### Table: `receipt_items`
Line items on each receipt (individual batch deduction records).

```sql
CREATE TABLE receipt_items (
    id              INTEGER PRIMARY KEY AUTOINCREMENT,
    receipt_id      INTEGER NOT NULL REFERENCES receipts(id),
    medicine_name   TEXT    NOT NULL,           -- Snapshot at time of sale
    batch_id        INTEGER NOT NULL REFERENCES batches(id),
    quantity        INTEGER NOT NULL,
    unit_price      REAL    NOT NULL,
    total_price     REAL    NOT NULL,
    created_at      TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

#### Table: `audit_logs`
Record of all significant system events.

```sql
CREATE TABLE audit_logs (
    id              INTEGER PRIMARY KEY AUTOINCREMENT,
    user_id         INTEGER REFERENCES users(id),
    action          TEXT    NOT NULL,           -- 'login' | 'sale' | 'inventory_add' etc.
    resource_type   TEXT,                       -- 'medicine' | 'batch' | 'user' etc.
    resource_id     INTEGER,
    details         TEXT,                       -- JSON string of additional context
    ip_address      TEXT,
    created_at      TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

#### Table: `licenses`
License key records (for license server).

```sql
CREATE TABLE licenses (
    id              INTEGER PRIMARY KEY AUTOINCREMENT,
    license_key     TEXT    NOT NULL UNIQUE,
    customer_email  TEXT    NOT NULL,
    status          TEXT    NOT NULL DEFAULT 'active',  -- 'active' | 'revoked' | 'expired'
    hardware_id     TEXT,                       -- NULL = unbound
    created_at      TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    expires_at      TIMESTAMP,
    revoked_at      TIMESTAMP

```

#### Table: `settings`
Key-value settings (tax rate, pharmacy info, etc.).

```sql
CREATE TABLE settings (
    key             TEXT    PRIMARY KEY,
    value           TEXT    NOT NULL,
    description     TEXT,
    updated_at      TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP

```

### 4.2 SQLAlchemy ORM Models

All models inherit from a shared `Base` declarative class. Use SQLAlchemy 2.0-style type annotations.

**`app/core/models.py`** (abridged for key fields):

```python
class User(Base):
    __tablename__ = "users"
    id: Mapped[int] = mapped_column(primary_key=True)
    email: Mapped[str] = mapped_column(unique=True, index=True)
    full_name: Mapped[str]
    hashed_password: Mapped[str]
    role: Mapped[str] = mapped_column(default="cashier")
    is_active: Mapped[bool] = mapped_column(default=True)
    is_licensed: Mapped[bool] = mapped_column(default=False)
    sessions: Mapped[List["UserSession"]] = relationship(back_populates="user")

class Medicine(Base):
    __tablename__ = "medicines"
    id: Mapped[int] = mapped_column(primary_key=True)
    name: Mapped[str] = mapped_column(index=True)
    batches: Mapped[List["Batch"]] = relationship(back_populates="medicine")
    reorder_threshold: Mapped[Optional[int]] = mapped_column(default=None)

class Batch(Base):
    __tablename__ = "batches"
    id: Mapped[int] = mapped_column(primary_key=True)
    medicine_id: Mapped[int] = mapped_column(ForeignKey("medicines.id"))
    batch_number: Mapped[str]
    expiry_date: Mapped[date]
    purchase_price: Mapped[float]
    selling_price: Mapped[float]
    quantity: Mapped[int] = mapped_column(default=0)
    medicine: Mapped["Medicine"] = relationship(back_populates="batches")

class Receipt(Base):
    __tablename__ = "receipts"
    id: Mapped[int] = mapped_column(primary_key=True)
    receipt_number: Mapped[str] = mapped_column(unique=True)
    cashier_id: Mapped[int] = mapped_column(ForeignKey("users.id"))
    items: Mapped[List["ReceiptItem"]] = relationship(cascade="all, delete-orphan")

class ReceiptItem(Base):
    __tablename__ = "receipt_items"
    id: Mapped[int] = mapped_column(primary_key=True)
    receipt_id: Mapped[int] = mapped_column(ForeignKey("receipts.id"))
    batch_id: Mapped[int] = mapped_column(ForeignKey("batches.id"))
    quantity: Mapped[int]

class License(Base):
    __tablename__ = "licenses"
    id: Mapped[int] = mapped_column(primary_key=True)
    license_key: Mapped[str] = mapped_column(unique=True, index=True)
    customer_email: Mapped[str]
    status: Mapped[str] = mapped_column(default="active")
    hardware_id: Mapped[Optional[str]]
    created_at: Mapped[datetime] = mapped_column(default=datetime.utcnow)
    expires_at: Mapped[Optional[datetime]]
```

### 4.3 State Management — Backend

The backend follows **stateless REST** principles. All session state is maintained client-side via JWT tokens stored in secure HttpOnly cookies.

**Global state containers:**

1. **Database Session**: Managed via `app/core/database.py` using FastAPI's dependency injection (`get_db` dependency). Sessions are scoped per-request and automatically closed.

2. **Configuration**: `app/shared/config.py` uses Pydantic `BaseSettings` to load from environment variables. Loaded once at startup.

3. **Cache (Optional)**: For read-heavy operations (e.g., medicine catalog, supplier list), use an in-memory `functools.lru_cache` or Redis layer. Do not cache write paths.

4. **Application State**: The FastAPI app instance (`app/main.py`) holds references to services that are initialized once at startup (e.g., license validator, background task scheduler).

### 4.4 State Management — Frontend

The frontend uses **Zustand** for global state management with the following stores:

| Store | Responsibility |
|-------|----------------|
| `useAuthStore` | User session (token, user object, role, permissions), login/logout, token refresh |
| `useCartStore` | POS cart (items, quantities, totals, applied discounts, insurance info) |
| `useInventoryStore` | Medicine catalog, batch list, low-stock alerts, search/filter state |
| `useLicenseStore` | License status, activation status, grace period countdown |
| `uiStore` | UI preferences (theme, sidebar state, active tab, modal states) |

## 5. API CONTRACT & ROUTING SPECIFICATIONS

### 5.1 Authentication & Authorization

#### Endpoints

| Method | Path | Auth | Role | Purpose |
|--------|------|------|------|---------|
| POST | `/api/v1/auth/login` | None | — | Authenticate user, issue JWT pair |
| POST | `/api/v1/auth/refresh` | None | — | Refresh access token from refresh token |
| POST | `/api/v1/auth/logout` | Bearer | User | Revoke refresh token (client-side) |
| POST | `/api/v1/auth/register` | None | Admin | Register a new user (admin-only) |

#### Request/Response Schemas

**`POST /api/v1/auth/login`**

_Request body (JSON):_
```json
{
  "email": "dr.smith@pharmacy.com",
  "password": "s3cur3P@ssw0rd!"
}
```

_Success response (200):_
```json
{
  "access_token": "eyJhbGciOiJIUzI1NiIs...",
  "refresh_token": "eyJhbGciOiJIUzI1NiIs...",
  "token_type": "bearer",
  "user": {
    "id": 1,
    "email": "dr.smith@pharmacy.com",
    "full_name": "Dr. Smith",
    "role": "pharmacist",
    "permissions": ["inventory.read", "inventory.write", "pos.checkout"]
  }
}
```

_Error responses:_
- `401 Unauthorized` — Invalid email or password
- `400 Bad Request` — Malformed JSON

#### JWT Claims

The access token contains these claims:
```json
{
  "sub": "1",                           // User ID
  "email": "dr.smith@pharmacy.com",
  "role": "pharmacist",
  "permissions": ["inventory.read", ...],
  "exp": 1724547600,                    // Expires in 8 hours
  "iat": 1724511600,
  "type": "access"
}
```

Refresh tokens contain:
```json
{
  "sub": "1",
  "email": "dr.smith@pharmacy.com",
  "exp": 1727187600,                    // Expires in 30 days
  "type": "refresh"
}
```

#### Permissions Matrix

| Role | Permissions |
|------|-------------|
| **Admin** | `pos.checkout`, `inventory.*`, `users.*`, `settings.*`, `reports.*` |
| **Pharmacist** | `pos.checkout`, `inventory.read`, `inventory.write`, `receipts.read`, `reports.read` |
| **Cashier** | `pos.checkout`, `inventory.read`, `receipts.read` |

### 5.2 POS Routes

All routes under `/api/v1/pos/`. Require `Bearer` auth with `pos.checkout` permission.

| Method | Path | Purpose |
|--------|------|---------|
| GET | `/api/v1/pos/medicines/search?q=amoxicillin` | Search medicines by name (typeahead) |
| POST | `/api/v1/pos/checkout` | Process a complete checkout (atomic transaction) |
| GET | `/api/v1/pos/receipts/{receipt_id}` | Fetch full receipt with line items |
| GET | `/api/v1/pos/receipts/{receipt_id}/print` | Get receipt in print-ready format (thermal text) |

**`POST /api/v1/pos/checkout` — Checkout Request**

## 7. ERROR HANDLING & SECURITY PROTOCOLS

### 7.1 Error Handling Strategy

#### Backend — Structured Exception Handling

All backend routes use FastAPI's exception handlers. Custom exceptions are defined in `app/shared/exceptions.py`:

```python
class AppException(Exception):
    """Base exception for all application errors."""
    def __init__(self, message: str, status_code: int = 500, error_code: str = "app_error"):
        self.message = message
        self.status_code = status_code
        self.error_code = error_code
        super().__init__(self.message)

class ValidationError(AppException):
    """Raised when input data fails validation."""
    def __init__(self, message: str):
        super().__init__(message, status_code=400, error_code="validation_error")

class InsufficientStockError(AppException):
    """Raised during checkout when a batch has insufficient quantity."""
    def __init__(self, medicine_name: str, available: int, requested: int):
        super().__init__(
            f"Insufficient stock for {medicine_name}: {requested} requested, {available} available",
            status_code=400,
            error_code="insufficient_stock"
        )

class DatabaseError(AppException):
    """Wrapper for SQLAlchemy or raw DB errors."""
    def __init__(self, message: str = "A database error occurred"):
        super().__init__(message, status_code=500, error_code="db_error")
```

A global exception handler catches all `AppException` subclasses and returns a consistent JSON error response:

```json
{
  "error": {
    "code": "insufficient_stock",
    "message": "Insufficient stock for Amoxicillin 500mg: 5 requested, 0 available",
    "details": {
      "medicine_name": "Amoxicillin 500mg",
      "requested": 5,
      "available": 0
    }
  }
}
```

#### Frontend — Global Error Boundary

The frontend has a top-level `ErrorBoundary` component that catches render-time errors and displays a friendly error page with a "Retry" button and a support contact link.

API errors are handled via an Axios response interceptor that:
1. Catches `401` responses and triggers a silent token refresh.
2. Catches `403` responses and redirects to a "403: Access Denied" page.
3. Catches `4xx` and `5xx` responses and displays a toast notification with the error message.
4. Catches network errors and shows "Unable to reach server. Please check your connection."

### 7.2 Security Protocols

#### Input Sanitization
- **Backend**: All Pydantic models enforce type validation, length limits, and pattern matching (e.g., email format). No raw SQL queries — all use SQLAlchemy parameterized queries.
- **Frontend**: All user inputs are validated client-side via Zod schemas (mirrors backend Pydantic models). Form submissions always re-validate server-side.
- **HTML Output**: Any HTML rendered from user input (e.g., medicine descriptions) must be sanitized via `bleach` or equivalent before storage/rendering.

#### Rate Limiting
- **Auth endpoints** (`/auth/login`, `/auth/register`): 5 requests per minute per IP.
- **All other endpoints**: 100 requests per minute per authenticated user.
- **License endpoints** (`/license/validate`, `/license/activate`): 10 requests per minute per license key.
- Implemented via `slowapi` middleware on the FastAPI backend.

#### CORS Policy
- Only the origin specified in `FRONTEND_URL` env var is allowed.
- Credentials (cookies) are allowed.
- All headers listed in `Access-Control-Allow-Headers` are explicitly permitted: `Authorization`, `Content-Type`, `X-Requested-With`.

#### Secrets Management
- All secrets (JWT secret, database passwords, license server secret) are read from environment variables via `Pydantic Settings`.
- `.env` files are in `.gitignore`.
- In production, secrets are injected via the deployment platform's secret management (e.g., PythonAnywhere environment variables).
- No secrets appear in logs, error messages, or client-side code.

#### Password Security
- Passwords are hashed with **bcrypt** (cost factor 12) via `passlib` library.
- Passwords must be at least 8 characters, contain uppercase, lowercase, and a number.
- Login attempts are limited to 5 per minute per IP + per account.
- Failed login attempts are logged with IP, timestamp, and account (if found).

#### JWT Security
- Access tokens expire in 8 hours; refresh tokens in 30 days.
- Tokens are stored in **secure, HttpOnly, SameSite=Strict** cookies (not localStorage) on the frontend.
- Token refresh is automatic via an Axios request interceptor.
- JWT secret is at least 64 characters of cryptographically random data.
- Token signature verification uses `HS256` algorithm exclusively.

#### License Security
- License keys are generated server-side using `secrets.token_urlsafe(32)` and formatted as `PHARM-XXXX-XXXX-XXXX`.
- Hardware ID is derived from a hash of: machine UUID + disk serial + MAC address (platform: Linux/Windows/macOS).
- License validation endpoint requires both `license_key` and `hardware_id` in the request body.
- On first validation, the license is bound to the hardware ID. Subsequent validations from different hardware IDs return `403`.
- A **grace period** of 7 days allows offline operation after the last successful online validation.

#### Audit Logging
All significant actions are logged as `audit_logs` entries:
- User login/logout
- POS checkout
- Inventory receive/adjust
- User creation/role change
- License validation
- Settings change

Each entry records: user_id, action, resource_type, resource_id, details (JSON), ip_address, timestamp.

#### Secure Headers
All backend responses include these headers:
```
X-Content-Type-Options: nosniff
X-Frame-Options: DENY
X-XSS-Protection: 1; mode=block
Referrer-Policy: strict-origin-when-cross-origin
Strict-Transport-Security: max-age=31536000; includeSubDomains
Content-Security-Policy: default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'
```

### 10.2 FastAPI Backend Integration

- Send a POST request from the Next.js frontend to `http://localhost:8000/api/v1/auth/login`.
- **Request format:** JSON body with `Content-Type: application/json`:
  ```json
  {"username": "string", "password": "string"}
  ```
- The payload must be structured as JSON (not Form Data) — the backend expects a Pydantic `LoginRequest` model.
- The backend returns a `Token` response:
  ```json
  {"access_token": "string", "refresh_token": "string", "token_type": "bearer", "user": {...}}
  ```
- On failure, the backend returns the uniform error contract: `{"error": {"code": "string", "message": "string", "details": {}}}`.

### 10.3 Secure Token Storage via Server Actions

- Upon successful authentication, extract the `access_token` from the response.
- Use Next.js Server Actions to set an HTTP-only cookie:
  - Cookie name: `access_token`.
  - `httpOnly: true` — prevents JavaScript access (XSS mitigation).
  - `sameSite: "strict"` — CSRF mitigation.
  - `secure: process.env.NODE_ENV === "production"` — HTTPS-only in production; disabled in dev (HTTP localhost).
  - `path: "/"` — available across the entire application.
  - `maxAge`: 8 hours (`480 * 60` seconds) — matches `ACCESS_TOKEN_EXPIRE_MINUTES` in backend config.
- Also set `refresh_token` as a separate HTTP-only cookie:
  - `maxAge`: 30 days (`30 * 24 * 60 * 60` seconds) — matches `REFRESH_TOKEN_EXPIRE_DAYS`.
- The Server Action must use `cookies()` from `next/headers` (App Router) or `res.cookies.set()` in API route handlers (Next.js 16+).

### 10.4 Redirect on Success

- After the HTTP-only cookie is set, automatically redirect the user to the `/dashboard` route.
- Use `redirect("/dashboard")` from `next/navigation` inside the Server Action, or `router.replace("/dashboard")` in the client component after the Server Action returns.

### 10.5 Error Handling & User-Friendly UI Messages

| Condition | HTTP Status | User-Friendly Message |
|---|---|---|
| Invalid username or password | 401 Unauthorized | "Invalid credentials" |
| Account locked (too many failed attempts) | 403 Forbidden | "Account locked due to too many failed attempts" |
| Network failure / backend unreachable | (fetch throws) | "Server unreachable" |
| Malformed request (missing fields) | 422 Unprocessable Entity | "Please check your input and try again" |
| Unexpected server error | 500 Internal Server Error | "An unexpected error occurred. Please try again later." |

- Error messages are displayed in the red alert banner on the login page.
- Network errors are caught via `try/catch` around `fetch` and surfaced as "Server unreachable".
- Backend error messages from the uniform error contract (`error.message`) are extracted and displayed.

### 10.6 Middleware Protection

- `middleware.ts` must protect the `/dashboard` route (and all routes under it) by checking for the `access_token` cookie.
- If no `access_token` cookie is present, redirect to `/login`.
- If an `access_token` cookie is present on `/login`, redirect to `/dashboard`.
